# Contributing to VisionUse

VisionUse is meant to be a framework people build on for years. That goal drives
most of what follows — particularly the parts that look strict.

Read [PRINCIPLES.md](PRINCIPLES.md) and [ARCHITECTURE.md](ARCHITECTURE.md) before
a first substantial change. [CLAUDE.md](CLAUDE.md) is the engineering standard and
applies to human and AI contributors alike.

---

## Setup

Requires Python 3.12+ and ffmpeg 6+.

```bash
uv sync
```

```bash
uv run vision doctor
```

`doctor` is the fastest way to find a broken environment. It names what is missing
and how to install it, and exits non-zero when anything blocks use.

## The three gates

Every change must pass all three, locally and in CI. They are not advisory.

```bash
uv run ruff check . && uv run ruff format --check .
```

```bash
uv run mypy
```

```bash
uv run pytest
```

To skip tests that need real media:

```bash
uv run pytest -m "not integration"
```

Speech-recognition tests download Whisper weights on first run, so they are
excluded from the default CI job and run in their own. To run them locally:

```bash
uv run pytest -m asr
```

Install the pre-commit hooks so failures surface before a push:

```bash
uv run pre-commit install
```

### Why the linter is this strict

The ruleset enforces things that are otherwise argued about in review, one PR at a
time, forever: docstrings on public API, complete type annotations, no `print`, no
blind `except`, no relative imports, no commented-out code. Encoding them in
`pyproject.toml` makes the standard uniform, reviewable by machine, and impersonal.
Reviewers get to spend attention on design instead of style.

Two rules are worth calling out because they look pedantic and are not:

- **`ANN401` (no bare `Any`)** — at the JSON and media boundaries, `Any` hides real
  contracts. Use `pydantic.JsonValue`, `object`, or the library's own types. PyAV
  ships stubs; use `VideoStream` and `InputContainer` rather than `Any`.
- **`T20` (no `print`)** — output is structured logging (`vision_use.log`) or Rich
  rendering in the CLI. A stray `print` corrupts `--json` output.

If a rule is genuinely wrong for a case, add a targeted `# noqa: RULE` **with a
comment saying why**. A bare `noqa` will be asked about in review.

## Tests

- Every feature needs tests. Bug fixes need a test that fails before the fix.
- Media fixtures are **generated by ffmpeg, never committed**. `tests/conftest.py`
  provides `make_clip(...)`; ask for the exact rate, size, or duration you need.
  This keeps the repository text-only and lets a test exercise an NTSC rate or a
  rotation flag without shipping a binary for each.
- Mark tests needing real media `@pytest.mark.integration` and guard them with
  `@requires_ffmpeg` so the suite still runs without ffmpeg installed.
- Determinism is a testable property here, not a hope. If you add an analyzer,
  assert that two runs produce identical output.

## Writing a skill or plugin

Skills are the unit of capability; adding one requires no change to the runtime.
Read [SKILL_SPEC.md](SKILL_SPEC.md) for the full contract.

### The four composability rules

A skill that breaks any of these will compose incorrectly with skills it has never
heard of, which is the failure mode hardest to debug and most damaging to trust.

1. **Return a `PlanPatch`, never a rendered file.** Pixels are produced exactly
   once, by the renderer, at export.
2. **Never import another skill.** Skills compose through the `EditPlan`, not
   through each other. A direct import creates an ordering dependency the runtime
   cannot see or resolve.
3. **Declare what you need in `meta.requires`.** Do not run your own decoder
   because the context lacks something — that is a gap in the context engine, and
   filling it privately means every other skill re-derives it too (Principle 8).
4. **Be idempotent given the same context, plan, and parameters.** The retry loop
   re-runs skills; a skill whose second run differs makes retry unsound.

### Skill behaviour has a recorded baseline

`tests/evals.golden.json` records what each M4 skill measured on a fixed
fixture. `test_no_skill_regressed` re-runs them and reports any measurement that
moved more than 2%, in either direction.

It also reports a **changed strategy**, because measurements can be identical
while the approach has changed completely — that is how a behaviour change hides
from a numeric baseline. `reframe` switching from a fixed crop to a following
one moved no measurement at all.

This catches the change no unit test can: a threshold nudged, a padding constant
tweaked, a grouping rule "improved". Those pass every unit test, because every
unit test was written to allow them.

**When it fails, decide whether the change was intended before regenerating.**
A baseline updated reflexively records the bug. Once you are sure:

```bash
uv run python -m tests.test_evals --update
```

Adding a *new* measurement is never a regression — that is how a skill gets
stricter, and it needs no baseline update.

### A baked effect carries a version

`EffectDef.version` is mixed into the bake cache key. Bump it whenever an
effect's *output* changes for identical parameters — a corrected algorithm, a
different constant. Nothing else in that key can see the implementation, so
without a bump every existing cache keeps serving what the old code produced.

### Effect schemas are additive-only

Effect parameters may only gain optional fields with defaults. A breaking change
is a **new effect type** (`crop` → `crop.v2`), with the old one deprecated but
still registered. See `PLAN.md` § D4 — this exists precisely so that third-party
effects never depend on plugin authors writing migrations correctly.

This is enforced, not trusted. `tests/schemas.golden.json` snapshots every
registered effect's JSON schema, and `test_no_effect_schema_changed_incompatibly`
fails on any non-additive diff — a removed property, a changed type, or an
optional field becoming required.

**When that test fails, updating the snapshot is almost always the wrong fix.**
It means every stored plan using that effect will silently break. Introduce a
new type instead:

```python
class CropV2Effect(EffectDef):
    effect_type: ClassVar[str] = "crop.v2"
    params_model: ClassVar[type[BaseModel]] = CropV2Params
```

and mark the old one `deprecated_since` / `superseded_by`, leaving it registered.

Adding a *new* effect is additive and needs no ceremony — but do regenerate the
snapshot so the new type is guarded from then on:

```bash
uv run python -c "import json,pathlib;from vision_use.effects import registry;from vision_use.effects.builtin import BUILTIN_EFFECT_TYPES;s=registry.schemas();pathlib.Path('tests/schemas.golden.json').write_text(json.dumps({k:s[k] for k in BUILTIN_EFFECT_TYPES},indent=2,sort_keys=True)+chr(10))"
```

The snapshot covers built-ins only. A plugin's schemas are the plugin's to
guard — otherwise having one installed would fail a test about this repository.

## Publishing a plugin

A third-party package adds a skill, an analyzer, or an effect through entry
points. **Nothing in this repository changes.**

The fastest start is a generated one — it installs, registers, and passes its
own discovery test out of the box:

```bash
uv run vision plugin new my-plugin
```

[docs/plugin-sdk.md](docs/plugin-sdk.md) is the full guide. The mechanism:

```toml
[project.entry-points."vision_use.skills"]
stabilize = "vision_stabilize:StabilizeSkill"

[project.entry-points."vision_use.effects"]
deshake = "vision_stabilize:DeshakeEffect"

[project.entry-points."vision_use.analyzers"]
motion = "vision_stabilize:MotionAnalyzer"
```

The published object may be the class or a zero-argument factory; both work.

Discovery happens **explicitly at the entry points** — the CLI callback and
`build_server()` — not at package import. Loading during a package's own import
would let a plugin that imports VisionUse re-enter a half-initialised module.

Check what an installation found:

```bash
uv run vision plugins
```

Two guarantees worth knowing when your plugin misbehaves:

- **A broken plugin never takes the framework down.** Its failure is caught,
  recorded against its entry-point name, and shown by `vision plugins`. One typo
  in a module path must not make `vision --help` fail.
- **A name collision is a loud error, not an override.** A plugin cannot
  silently shadow a built-in skill or effect; the registration fails and the
  reason says so.

## Dependencies

Every new dependency must be justified in the PR. Answer these:

- What does it do that the standard library or an existing dependency cannot?
- Is it actively maintained?
- Does it work on CPU only? GPU acceleration may be optional; a CPU path is not.
- What does it pull in transitively, and does anything collide with what we have?

That last question is not theoretical. `scenedetect` requires `opencv-python`,
which installs the same `cv2` module as `opencv-python-headless` — declaring both
installs OpenCV twice and removing either breaks the other. OpenCV also bundles
its own libav, which warns against PyAV's on macOS. Both facts are recorded in
`TASKS.md` § Decisions log; add yours there when you hit something similar.

## Commit messages

[Conventional Commits](https://www.conventionalcommits.org): `feat:`, `fix:`,
`docs:`, `refactor:`, `test:`, `chore:`, with `!` or a `BREAKING CHANGE:` footer
for anything that breaks an existing plan, schema, or public API.

This is not bookkeeping for its own sake — release notes are generated from the
commits since the last tag, so the log is what users read when deciding whether
to upgrade.

## Releasing

Releases are **tag-driven**, not commit-driven. Merging to `main` publishes
nothing; releasing is a decision, and the tag is where that decision is
recorded.

1. Bump `version` in `pyproject.toml`.
2. Merge that to `main`.
3. Tag it and push:

```bash
git tag v0.2.0 && git push origin v0.2.0
```

`release.yml` then verifies the tag matches the packaged version, runs all three
gates, publishes to PyPI via trusted publishing (no token in secrets), pushes
the image to `ghcr.io`, and generates the release notes.

**The tag-version check exists because a mismatch is silent otherwise**: `pip
install vision-use==0.2.0` would install a package that calls itself something
else. A tag containing a hyphen (`v0.2.0-rc1`) is published as a prerelease.

## Pull requests

Include:

**Purpose** — what problem this solves, in a sentence or two.

**Design decisions** — what you chose and what you rejected. This is the most
valuable section; a year from now it is the only record of why the code looks the
way it does.

**Tests** — what you added, and what failure they would catch.

**Performance impact** — especially anything touching decode, encode, or the
cache. Note memory behaviour on long files: streaming is required, whole-file
loads are not acceptable.

**Future considerations** — known gaps, deferred work, anything a follow-up
should pick up.

If a change alters a decision recorded in `TASKS.md` § Decisions log, update that
entry in the same PR. A stale decisions log is worse than none.
